# The QR code: TLV + Base64

Read this when generating, debugging or reviewing the QR on a Saudi e-invoice.

## Structure

The QR does not contain a URL or JSON. It contains one Base64 string. Decoded, that string is a sequence of TLV records:

```
[tag: 1 byte][length: 1 byte][value: `length` bytes][tag][length][value]...
```

- **Tag**: a number from 1 to 9.
- **Length**: the number of **bytes** in the value after UTF-8 encoding. Not characters.
- **Value**: UTF-8 text for tags 1–5.

Then Base64-encode the whole byte sequence. Standard Base64 with `=` padding, not URL-safe Base64.

## Tags

Source: ZATCA Security Features Implementation Standards v1.2 (2023-05-19), section 4, Table 3.

| Tag | Field | Required from | Value bytes |
|---|---|---|---|
| 1 | Seller name | 4 Dec 2021 | UTF-8 text |
| 2 | Seller VAT registration number | 4 Dec 2021 | UTF-8 text |
| 3 | Invoice timestamp, ISO 8601 (the standard's example: `2022-02-21T12:13:57Z`) | 4 Dec 2021 | UTF-8 text |
| 4 | Invoice total with VAT | 4 Dec 2021 | UTF-8 text |
| 5 | VAT total, the value of BT-110 in the XML | 4 Dec 2021 | UTF-8 text |
| 6 | Hash of the XML invoice | 1 Jan 2023 | Base64 **text** of the SHA-256 hash (44 bytes) |
| 7 | ECDSA signature of the invoice hash | 1 Jan 2023 | Base64 **text** of the DER signature (about 96 bytes) |
| 8 | ECDSA public key from the signing key | 1 Jan 2023 | **Raw** DER SubjectPublicKeyInfo bytes (88 bytes for secp256k1) |
| 9 | ZATCA CA's signature on the stamp certificate. **Simplified tax invoices and their notes only** | 1 Jan 2023 | **Raw** DER ECDSA signature bytes (about 70–72 bytes) |

Tags go in order, 1 to 9. The whole payload, once Base64-encoded, may be at most 700 characters (section 4.1).

### How tags 6 to 9 really look

The byte formats above are read from the QR in ZATCA's own SDK sample (`Data/Samples/Simplified/Invoice/Simplified_Invoice.xml`), and both bundled scripts check them in their self-test:

- Tag 6 equals the invoice's first `ds:DigestValue` (Base64 text, 44 bytes). The standard's prose says the hash "is 32 bytes", but ZATCA's SDK puts the 44-byte Base64 text in the QR. Follow the SDK; its validator is what checks you.
- Tag 7 equals `ds:SignatureValue` (Base64 text).
- Tag 8 is the certificate's public key as raw DER. Its algorithm OID is `1.3.132.0.10`, which is secp256k1.
- Tag 9 is byte-for-byte the `signatureValue` of the X.509 certificate in `ds:X509Certificate`, the CA's signature over your certificate. It is not a signature over the invoice.

For standard tax invoices (B2B), FATOORA builds the QR during clearance and returns it in the cleared XML. Your system only renders it (Detailed Guidelines v2, FAQ "When will the QR code string be generated by ZATCA for Tax Invoices").

`scripts/qr-tlv.*` **decodes** tags 6–9 and checks their shape. It does not create them: they come from your signing step (see `phase2-overview.md`).

## Worked example, byte by byte

```
01 0C "Bobs Records"            tag 1, 12 bytes
02 0F "310122393500003"         tag 2, 15 bytes
03 14 "2022-04-25T15:30:00Z"    tag 3, 20 bytes
04 07 "1000.00"                 tag 4, 7 bytes
05 06 "150.00"                  tag 5, 6 bytes
```

Base64 of those 70 bytes:

```
AQxCb2JzIFJlY29yZHMCDzMxMDEyMjM5MzUwMDAwMwMUMjAyMi0wNC0yNVQxNTozMDowMFoEBzEwMDAuMDAFBjE1MC4wMA==
```

This is the sample that circulates in ZATCA guidance and many libraries. Both scripts reproduce it byte for byte in their self-test.

## The Arabic name trap

Most Arabic letters take 2 bytes in UTF-8. `"شركة السجلات المحدودة"` is 21 characters but 40 bytes. Writing 21 as the length corrupts every tag after it, and validators report the QR as invalid.

```js
// Wrong
Buffer.from([1, name.length])
// Right
const value = Buffer.from(name, "utf8");
Buffer.concat([Buffer.from([1, value.length]), value]);
```

```python
# Wrong: len(name)
# Right:
value = name.encode("utf-8")
bytes([1, len(value)]) + value
```

The same bug happens in PHP (`strlen` is right, `mb_strlen` is wrong here), C# (`Encoding.UTF8.GetByteCount`, not `.Length`) and Java (`getBytes(StandardCharsets.UTF_8).length`).

## Values

- **Seller name**: the registered name. Arabic is fine and common.
- **VAT number**: 15 digits, first and last digit 3 (rule BR-KSA-40).
- **Timestamp**: the invoice's issue date and time in ISO 8601, matching the XML. In ZATCA's SDK sample, `IssueDate` 2022-08-17 and `IssueTime` 17:41:08 become tag 3 `2022-08-17T17:41:08Z`. Build tag 3 from the same two fields so they never disagree.
- **Amounts**: plain decimal text with a dot and two decimals: `1150.00`. No currency symbol, no thousands separators, no Arabic-Indic digits.
- **Length limit**: one length byte means a value can be at most 255 bytes, and the Base64 payload at most 700 characters.

## Common reasons a QR fails validation

1. Length counted in characters, not bytes (Arabic names).
2. URL-safe Base64 (`-` and `_`) instead of standard (`+` and `/`).
3. Amounts formatted for display: `١٬١٥٠٫٠٠`, `1,150.00`, or `SAR 1150`.
4. Tags out of order, or a JSON/URL encoded instead of TLV.
5. Phase 2: only tags 1–5 present because the device was never onboarded, so there is nothing to put in tags 6–9.
6. Phase 2: tags 6–9 in the wrong form. Tag 6 and 7 must be Base64 text; tag 8 and 9 must be raw DER bytes. Putting Base64 text in tag 8, or the raw 32-byte hash in tag 6, fails the SDK's QR check.
7. Phase 2: tag 9 added to a standard tax invoice, or left out of a simplified one.
8. Totals in the QR do not match the totals in the invoice body (tag 5 must equal BT-110).

## Debugging a QR you received

Scan it with any QR reader to get the Base64 text, then:

```bash
node scripts/qr-tlv.mjs decode "PASTE_BASE64"
python3 scripts/qr_tlv.py decode "PASTE_BASE64"
```

Both print every tag with its byte length, and fail loudly on truncated or malformed payloads.
